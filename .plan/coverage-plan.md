# @gtkx/animated: framer-motion coverage plan

## 1. Where coverage stands

Three numbers, each measured differently, because they tell opposite stories.

| Axis | Live | Notes |
|---|---|---|
| **Component props** (`MotionNodeOptions`) | ~95% | `types.ts:60` does `Omit<MotionNodeOptions, …>` and re-adds 11 GTK-retyped props, so every framer prop is at least *typed*. `split-motion-props.ts:15` delegates routing to framer's own `isValidMotionProp`, so nothing leaks to the widget by accident. |
| **Feature bundles** | 9/9 = full `domMax` parity | `features/register.ts:12-37` registers animation, exit, hover, tap, focus, inView, pan, drag, layout. `focus` and `inView` are GTK-native reimplementations; both `ProjectionNode` slots are `WidgetProjectionNode`. `isEnabled` predicates are restated verbatim from framer's `definitions.mjs:3-22`. |
| **Runtime export surface** | 33 of ~383 names ≈ **8.6%** | `index.ts:4-40` re-exports 35 names, 2 of them type-only. The other ~350 are unreachable, and roughly 250 of those are pure JS that would work verbatim. |

So the engine is close to complete and the **API surface is the gap**. That asymmetry is the whole plan: the largest single win is a mechanical edit to one file.

### Tier 2: moderate GTK glue

**W25. `filter` / `boxShadow` "none" keyframes.** ~50 lines. Port `isNone` and `makeNoneKeyframesAnimatable` verbatim (neither is exported from motion-dom) and subclass `KeyframeResolver` (default `isAsync = false`), assigning it to `WidgetVisualElement.KeyframeResolver`. The template must be the **first non-`"none"` string with complex values**, not the final keyframe — `getAnimatableNone("filter", "none")` is the identity, so a final-keyframe rule leaves the common exit direction `["blur(4px)", "none"]` broken while `["none", "blur(4px)"]` passes a probe. **W26. Keyboard press (Enter → `whileTap`/`onTap`).** ~40 lines, all in `bridge/widget-event-bridge.ts`. In `ensurePress`: `proxy.widget.setFocusable(true)` (GTK widgets are not focusable by default, and `target.tabIndex = 0` is inert on a plain `EventTarget`), attach a `Gtk.EventControllerKey`; on `key-pressed` with `Gdk.KEY_Return`/`KEY_KP_Enter` call `beginPress(context, {x:0,y:0}, "mouse", 0)`; on `key-released` call `endPress` with `"pointerup"`; on the existing focus-`leave` path call `endPress` with `"pointercancel"`. Tear down under the existing `listenerCountOf(proxy, "pointerdown") === 0` block. **Do not route through motion's `keyboard.mjs`** and **do not add `offsetHeight`** (traps).

**W27. `viewport.margin` percentages.** ~15 lines. Carry `{value, unit}` per side and resolve inside `viewportRectOf`, which already holds `viewport.getWidth()`/`getHeight()`: top/bottom against height, left/right against width, matching the `rootMargin` spec. `features/in-view.ts:27-43,58-64,74`.

**W28. `inView()` / `useInView()`.** ~180 lines. Factor `observeInView(widget, options, onChange): () => void` out of `InViewFeature`; everything needed already sits in the file as free functions or private methods (`measureIntersection` :66-80, `viewportRectOf` :58-64, `parseViewportMargin` :33-43, `reachesViewportAmount` :45-49, `resolveViewportWidget` :89-90, the adjustment/surface/map-unmap subscriptions :140-156,215-216, the bounded `frame.read` chain :122-138). `InViewFeature` becomes a thin consumer. Then export gtkx-owned `inView(widget, onStart, options)` with framer's onStart→onEnd contract and a `useInView(ref: WidgetRef, options)` on top. The observer needs **per-target registration with `unobserve`** (framer calls it whenever `onStart` returns a non-function, which is exactly the `once` path) and an **unconditional initial emit** (`applyChange` early-returns on unchanged state, which would swallow the first callback for already-visible widgets). **Do not stub `IntersectionObserver`** (trap).

**W29. Drag suppression on a text-input child.** ~25 lines. `isElementTextInput` is gated on `target !== element`, and gtkx never produces a differing target: `beginPress` dispatches with no `target`, so `dispatchEvent` sets `event.target = proxy = element`. Fix requires hit-testing: `proxy.widget.pick(local.x, local.y, Gtk.PickFlags.DEFAULT)` (Gtk-4.0.gir:179663), map through `proxyFor`, pass as `target` in the pointerdown init, plus a `tagName` getter returning `"INPUT"` for the six concrete `Gtk.Editable` implementors (`Text`, `Entry`, `SpinButton`, `SearchEntry`, `PasswordEntry`, `EditableLabel` — `instanceof Gtk.Editable` works at runtime via the generated `static [Symbol.hasInstance]`) and `"DIV"` as the catch-all, **not** `"BUTTON"`. The down/up target asymmetry is fine: `press()` uses `isNodeOrChild(target, upEvent.target)` and `parentElement` already walks `widget.getParent()`.

**W30. First-allocation projection re-measure.** ~40 lines. This is the root cause of the `dragConstraints` ref bug and of Reorder's degenerate ordering. `onLayoutMeasure` fires once per element at mount, before GTK size-allocate, delivering `min=0/max=0`; measured on a real drag, a 200px container clamped at 200 instead of 123, and a Reorder port reported `["a:0-0","b:0-0","c:0-0"]` while the widgets were allocated 800x40. framer resolves ref constraints once (`resolveConstraints` only re-resolves when `!this.constraints`), so it never self-corrects. Fix: re-fire the projection `measure` on the first size-allocate via the frame clock (`scheduleAfterLayout` in `packages/react/src/utils/frame-sync.ts` is the existing primitive; `Gtk.Widget` has no `size-allocate` signal and no `width`/`height` properties, so tick polling on `get_width()`/`get_height()` is the only route). Optionally mirror `updateSnapshot`'s existing zero-length guard (`create-projection-node.mjs:541-548`) in `updateLayout`.

**W31. `useDragControls` handle drag.** ~20 lines. Export a `useDragHandle(ref, controls)` that does `proxyFor(widget).addEventListener("pointerdown", e => controls.start(e))`. `ensureBridgeControllers` then attaches the click+drag gestures to the *handle*, and those already dispatch `pointermove`/`pointerup` to `motionWindow`, which is exactly what the PanSession listens on. The `listenerCountOf(motionWindow, "pointermove") > 0` claim gate works out because `start()` runs synchronously inside the `pointerdown` dispatch. This makes `pointerEventFromController` redundant — delete it, and rewrite `website/guide/css-and-animations.md:241-262`.

**W32. `propagate.tap: false`.** ~50 lines, no root pointer bus needed. GTK has a native mechanism the bridge already uses: `gtk_gesture_set_state(GTK_EVENT_SEQUENCE_CLAIMED)` at `widget-event-bridge.ts:162`. `GestureClick` is default BUBBLE phase (target-first), so claiming in the target's `pressed` handler denies the ancestor's gesture. The catch the naive version misses: `attachDragGesture` is `PropagationPhase.CAPTURE` and its `drag-begin` also calls `beginPress`, so an ancestor dispatches pointerdown *before* the descendant's click gesture runs. A claim-only fix therefore fires ancestor `onTapStart` then `onTapCancel`, when framer's contract is that the ancestor receives nothing. The CAPTURE-phase `beginPress` dispatch must be gated too, and `propagate?.tap` has to be threaded onto the `WidgetProxy` (no path exists today).

**W33. `usePageInView`.** ~60 lines. Make the `document` stub an `EventTarget` subclass with a `hidden` field dispatching `visibilitychange`. Drive it from **`GdkToplevel:state` tested against `GDK_TOPLEVEL_STATE_MINIMIZED`** (Gdk-4.0.gir:35338, 35983), aggregated across toplevels, **not** `Gtk.Window:is-active` (trap). Needs the toplevel-enumeration and `items-changed` rescan currently private inside `projection/root.ts:9-64` extracted into a shared module; note surfaces only exist after realize, so it inherits the same realize deferral. Also change `global.d.ts:5` from `var document: object`.

**W34. `Reorder.Group` / `Reorder.Item`.** ~200 lines, plus W30 as a hard prerequisite. framer exports only the `Reorder` namespace; `ReorderContext` and `checkReorder` are internal, and `Group`/`Item` hardcode `as="ul"`/`as="li"` via `useConstant(() => motion[as])`, so they must be reimplemented over `animated` + `useDragControls`. `checkReorder` is 19 lines and its two dependencies (`mixNumber`, `moveItem`) are public. Drop auto-scroll (it is `getComputedStyle` + `window.scrollBy`). `onLayoutMeasure` survives the prop split (`isValidMotionProp` matches `onLayout*`). Without W30, `onReorder` still fires — which is why a naive port looks green — while every item's layout box is `0-0` and a 1px drag swaps immediately. `zIndex` has no GTK equivalent, so the dragged item paints under later siblings.

**W35. Scroll surface + `useScroll` / `scroll` / `scrollInfo`.** ~200 lines, the largest coherent unlock left. The mapping is exact: `scrollTop`/`scrollLeft` = `adjustment.getValue()`, `clientHeight`/`clientWidth` = `getPageSize()`, `scrollHeight`/`scrollWidth` = `getUpper() - getLower()`. Note `scrollLength = scrollHeight - clientHeight` must come out as `upper - page_size`, GTK's actual max scroll value — deriving `clientHeight` from `widget.getHeight()` instead is wrong because the allocation includes frame border and non-overlay scrollbars. Pieces:
- Scroll geometry getters on `WidgetProxy` resolving the nearest `Gtk.ScrolledWindow` (~40).
- A `scroll` event source in `widget-event-bridge.ts` connecting **both** `value-changed` **and** `changed` (the `changed` half substitutes for the missing `ResizeObserver` on content-size changes) with symmetric teardown (~35).
- `offsetLeft`/`offsetTop`/`offsetParent` (~25), computed **scroll-independently** — `gtk_widget_compute_bounds` resolves the transform chain and therefore *includes* viewport scroll, which is the opposite of DOM `offsetTop` (trap).
- A gtkx `useScroll` wrapper resolving a container from a widget ref, since `useScroll({target})` alone returns four MotionValues frozen at 0 (`document.scrollingElement` is undefined so `scroll()` returns `noop`) (~25).
- An `SVGGraphicsElement` stub or an `isHTMLElement`-satisfying shape so `calcInset` does not hit `current instanceof SVGGraphicsElement` → `ReferenceError`.
- Exports (~5).

`supportsScrollTimeline` is correctly false (`window.ScrollTimeline` absent), so everything routes through `scrollInfo`, which is the path this glue serves.

**W36. `ResizeObserver` shim.** ~110 lines, and it must land **after** W30. `Gdk.Surface::layout` is a toplevel signal and is the wrong unit: a container that grows because a `Gtk.Paned` divider moved or a `Revealer` expanded emits nothing, which is exactly the case the observer exists for. Build it on per-widget tick polling of `get_width()`/`get_height()` via `scheduleAfterLayout`. It cannot live in `motion-env.ts` (that module is imported by `widget-proxy.ts`, so a back-import cycles) — put it in its own module and duck-type on `"widget" in target`. **The first notification calls `scalePositionWithinConstraints`, which does `visualElement.current.style.transform = "none"` unconditionally**; see traps.

### Tier 3: expensive

**W37. Root pointer bus.** ~280 lines. Unlocks `globalTapTarget`, DOM-order nesting, and correct nested press/drag teardown in one structure. Must be **per `Gtk.Native`**, not per window: `GtkPopover`, dialogs, and menus each own a `GdkSurface`, and a window-rooted `pick()` cannot address widgets inside a popover's surface at all. Must subtract `gtk_native_get_surface_transform` before picking — `gdk_event_get_position` returns surface coordinates while `gtk_widget_pick` takes widget coordinates, and under CSD every window has a nonzero offset. On a plain undecorated test window the offset is 0, so a probe passes and every real tap lands on the wrong widget. The ancestor walk must set `target` explicitly (Node reassigns it per dispatcher otherwise, breaking the pointerup success test) and carry event *identity* (motion's `stopPropagation` option is a WeakSet, not `event.stopPropagation()`). `SyntheticEvent`'s `currentTarget` is currently defined non-configurable and would throw on the second hop. Keep the claiming `GestureDrag` or an ancestor `GtkScrolledWindow`/`GtkListView` steals motion drags mid-gesture.

**W38. Nested press/drag session isolation.** Subsumed by W37. The bridge-local fix does not exist: `press` and `PanSession` register their end listeners on `window`, never on the target, so "dispatch pointercancel on the proxy for the non-owner" reaches zero listeners and leaves a stale session subscribed to `motionWindow` `pointermove`, which then consumes the next unrelated drag. Ownership is also ill-defined, since `beginPress` fires from a CAPTURE gesture (ancestor-first) and a BUBBLE gesture (descendant-first).

**W39. `AnimatePresence mode="popLayout"`.** ~500 lines across `packages/react` and `packages/codegen`, not `packages/animated`. `GtkOverlay` is the right primitive (`gtk_overlay_add_overlay` + `set_measure_overlay`), but the overlay slot is not reachable from JSX: `built-ins.ts:109` registers `GtkOverlay` in `SINGLE_CHILD_TYPES` whose only ops are `setChild`/`setChild(null)`. Moving the exiting widget from `children` to an `overlay` prop is a remove-then-append across two distinct `ContainerProp`s, which the reconciler executes as destroy+create — and a destroyed widget cannot finish an exit animation. Needs a new cross-prop move operation in `container-attach.ts`/`host-config.ts`. Do **not** approximate with animated negative margins: that produces a *gradual* collapse, which is precisely the "sync" behavior popLayout exists to avoid, and layout-animating siblings would measure a moving target through `getBoundingClientRect` every frame. Today popLayout degrades silently to "sync" (`isHTMLElement` is false, so the measure never runs), which is an acceptable resting state.

## 3. Traps: stubs that pass framer's probe and then lie

These are the ones to write down somewhere permanent, because each is a plausible-looking one-liner.

| Trap | What breaks |
|---|---|
| **A `style` object on `WidgetProxy`** | `setStyle`/`addStyleValue` write `element.style[key]`; gtkx renders through a generated `Gtk.CssProvider` rule. The stub absorbs every write and drops it, converting an honest failure into a silent one, and additionally makes the `DOMKeyframesDefinition` arm of `animate(element, …)` appear to succeed |
| **Making `WidgetProxy` extend the `Element`/`HTMLElement` stubs** | Flips the `createDOMVisualElement` branch at `animate/subject.mjs:32` **and** the WAAPI gate at `waapi.mjs:27`. The JS animation path is the only one that can reach a GTK CSS rule |
| **`offsetHeight` on `WidgetProxy`** | `isHTMLElement` is `"offsetHeight" in element`, so this flips globally. `press()` then enters its focus block and calls `target.hasAttribute("tabindex")` → TypeError on every `whileTap` component. `calcInset` goes from returning `{0,0}` to returning `{NaN,NaN}`. `effects/style/index.mjs:17` changes branch. It gates exactly one thing you might want (the press keyboard path) and nothing else |
| **Installing `DOMKeyframesResolver`** | `positionalKeys` includes all of `transformPropOrder`, and `positionalValues` has entries for `x`, `y`, `translateX`, `translateY`. `animate={{ x: ["-100%", 0] }}` — the canonical slide-in — sets `needsMeasurement`, reads `getComputedStyle` (`{}`), `parseValueFromTransform(undefined)` returns 0, and the animation becomes 0 → 0. No error. It also flips every resolution to async and injects a transform-removal write pass |
| **Stubbing `IntersectionObserver` on `globalThis`** | `inView()` calls `resolveElements` **before** constructing the observer. gtkx external refs hold a raw `Gtk.Widget`, which is not an `EventTarget` and is not iterable, so `Array.from` yields `[]`: it observes nothing and returns a no-op disposer. Separately, `amount` is converted to a numeric `threshold` (`"some"`→0) before the observer sees it, and `reachesViewportAmount` treats a numeric amount as `ratio >= amount`, so threshold 0 reports **everything permanently in view**, including unmapped widgets |
| **A `tagName` getter alone for text-input drag suppression** | `isElementTextInput` is gated on `target !== element`, and gtkx never produces a differing target. The getter is dead code. `"BUTTON"` as the catch-all is also wrong data: it tells `isElementKeyboardAccessible` that `GtkBox` and `GtkLabel` are natively focusable |
| **`window.getComputedStyle` returning a thin record** | `DOMKeyframesResolver` passes it straight into `positionalValues[name](box, style)`, which reads `top`/`left`. Without them, `parseFloat(undefined)` → NaN for every top/left/right/bottom keyframe. `boxSizing` must be `"border-box"` or width/height silently subtract paddings |
| **Dispatching `"resize"` on `motionWindow`** | `scalePositionWithinConstraints` unconditionally executes `this.visualElement.current.style.transform = "none"` for ref constraints → TypeError. With a `style` stub it is worse: framer strips the transform specifically so `updateLayout()` measures the untransformed box, and a stub that swallows the write leaves the transform applied, producing wrong constraints. Dispatching inside the surface layout handler also measures before GTK re-allocates |
| **A `ResizeObserver` built on `Gdk.Surface::layout`** | Silences the `typeof ResizeObserver === "undefined"` probe while never firing for the case that matters: content-driven resize with an unchanged toplevel |
| **Splicing `"scaleZ"` into `transformPropOrder`** | `numTransforms` is captured as a module-local at load (`transformPropOrder.length`), and two other constants (`positionalKeys`, `nonTranslationalTransformKeys`) are derived eagerly. The splice cannot run first, so the loop reads indices 0..16 of an 18-element array and **`skewY` silently stops emitting**. If scaleZ is wanted, patch motion-dom via pnpm |
| **Whitelisting `backdropFilter` without a value-type alias** | No `backdropFilter` entry exists in `defaultValueTypes`, so it falls to `complex`, whose `getAnimatableNone` zeroes every number: `brightness(0)`, `saturate(0%)`, transparent drop-shadow. The declaration serializes fine; the interpolation is wrong |
| **Wiring `GestureClick::cancel` → `endPress`** | Our own `drag.setState(CLAIMED)` at 3px synchronously cancels the click gesture (the drag is CAPTURE, the click is BUBBLE, so `gesture_phase_is_before` is false and GTK cancels rather than denies). Every drag would die on its first claimed frame, and `pressActive=false` would then swallow `drag-end` |
| **An `activePress` owner flag for nested gestures** | Dispatching `pointercancel` on the proxy reaches zero listeners (press and PanSession listen on `window`), so the non-owner's session never tears down and consumes the next drag |
| **`globalTapTarget` via per-widget `GestureClick`** | Misses presses on unproxied widgets, window chrome, and native children that claim the sequence; and nested proxied widgets each mint a distinct `SyntheticEvent`, so framer's identity WeakSet cannot dedupe — one physical press yields N `onTapStart` calls |
| **Routing keyboard press through motion's `keyboard.mjs`** | It does `new PointerEvent(type, { isPrimary: true, bubbles: true })`, and `SyntheticEvent`'s constructor `Object.assign`s the init onto an `Event`. `bubbles` is getter-only → `TypeError: Cannot set property bubbles`. Verified in Node |
| **Forwarding a received event to `motionWindow`** | Re-dispatching an in-flight `Event` throws `The event "x" is already being dispatched`. Synthesize a fresh `SyntheticEvent` with `target` set to the proxy, as `endPress` already does. Getting this wrong yields `onTapStart` + `onTapCancel` and never `onTap`, while `whileTap` still latches correctly — so a probe watching only `whileTap` passes |
| **`offsetTop`/`offsetLeft` from `compute_bounds`** | `gtk_widget_compute_bounds` resolves the widget transform chain, and `GtkViewport` applies scroll as a translation in that chain, so the value moves by `-scroll` while `info.current` moves by `+scroll`. They cancel and `progress` stays pinned instead of sweeping 0→1. DOM `offsetTop` deliberately excludes ancestor scroll |
| **Widening `scrollOffsetsOf` to `Gtk.Scrollable`** | A `GtkScrolledWindow` and its scrollable child **share one `Gtk.Adjustment`** (documented on the property, and verified: `sw.getVadjustment() === tv.getVadjustment()`). `removeElementScroll` translates once per path node, so the same offset is subtracted twice. If the child is the right source, it must be a replacement, not a widening |
| **Driving `document.hidden` from `Gtk.Window:is-active`** | That is keyboard focus. A fully visible window that merely lost focus would report hidden and stop animations the user is watching. `GdkToplevel:state & MINIMIZED` is the correct signal |
| **Adding `layoutRoot` to `needsProjection`** | `layoutRoot` needs a snapshot, and `willUpdate` gates snapshotting on `layoutId !== undefined \|\| layout`. The node's options would carry the flag (probe green) while nothing changes, and a snapshot-less node would be inserted into the relative-parent chain |
| **`rootNode.setOptions({ layoutScroll: true })` for "parity" with `DocumentProjectionNode`** | Every consumer of root scroll either excludes the root by construction or would translate by zero, since `measureScroll` is hardcoded to `{x:0,y:0}`. It only activates a dead `checkIsScrollRoot` stub |
| **Tracking "user overrides" of `MotionGlobalConfig.instantAnimations`** | framer owns that field as transient internal state: it sets it true inside `startInstantLayoutTransition` and false two postRender frames later. Any override-detection latches on framer's own writes and permanently pins it false, killing the `gtk-enable-animations` bridge |
| **Re-exporting `LazyMotion` / `domMax` / `domAnimation`** | `loadFeatures` is a **global, permanent, un-scoped merge** into the same table `features/register.ts` writes. `<LazyMotion features={domAnimation}>` would overwrite gtkx's `FocusFeature` with framer's DOM `FocusGesture` and `InViewFeature` with the IntersectionObserver one; `domMax` additionally replaces `WidgetProjectionNode` with `HTMLProjectionNode`. The damage hits every already-mounted widget in the process and is never undone on unmount |
| **Re-exporting `isMotionComponent` / `unwrapMotionComponent`** | The predicate requires `typeof component === "object"` (framer stamps a `forwardRef` object). gtkx's `Animated` is a plain arrow function, so it returns false even after stamping the symbol. If you want this, ship gtkx-named predicates that accept functions, and stamp the key string in the Proxy branch so intrinsics unwrap to `"GtkBox"` |
| **Resolving `vw`/`vh` at serialize time** | `serializeStyle` runs from `renderInstance`; nothing re-serializes on window resize, so a `50vw` would freeze at its mount value. Worse, `setWindowWidth` runs from the lazy root projection mount, so `innerWidth` is very plausibly still `0` at first serialization and `50vw` becomes `0px` permanently |
| **Hard-throwing in `serializeStyle` for SVG props** | It runs inside framer's render batch on every frame, so a throw kills every other property on that widget, and it fires for a purely static `style={{ fill: "red" }}` copied from web code. The existing warn-once-and-drop is the correct behavior |
| **Adding `presenceAffectsLayout`'s DOM siblings back** | `root`/`anchorX`/`anchorY` only configure `PopChild`'s absolute-positioning anchor; keep them omitted |

## 4. Verified non-gaps: do not touch

Each of these was investigated and is already correct. Writing glue for them is net negative.

| Thing | Why it is fine |
|---|---|
| **Multitouch / `isPrimary`** | `GestureClick` and `GestureDrag` both derive from `GestureSingle`, which "sticks to the first interacting sequence" — a second concurrent touch never reaches `beginPress`. `state.pressActive` guards it a second time. A `getSequences()` comparison would have no reachable false branch |
| **`pointercancel` from an external gesture claim** | GTK's cancel broadcasts iterate *all* of a widget's controllers, so the existing `drag.on("cancel")` already covers every case that could strand a press |
| **`setPointerCapture` / `releasePointerCapture`** | Zero call sites in framer-motion 12.42.2. GTK's implicit grab plus `endPress`'s target logic already reproduces DOM release-outside semantics |
| **Gesture teardown on `AbortSignal`** | `setupGesture` aborts an `AbortController`, and Node routes signal-driven removal through the subclass override, so `WidgetProxy.removeEventListener` runs and `releaseBridgeControllers` fires |
| **WAAPI fallback** | The `subject instanceof HTMLElement` gate short-circuits before the `Element.prototype.animate` and `document.createElement` probes, so the JS driver is always chosen and nothing throws |
| **`prefersReducedMotion` / matchMedia** | `settings-bridge.ts` sets `hasReducedMotionListener.current = true` before any element mounts, preempting `initPrefersReducedMotion` entirely |
| **`whileFocus`** | `FocusFeature` reproduces `:focus-visible` via `Gtk.Window.getFocusVisible()` |
| **`whileInView` + `viewport.root`/`once`/`amount`** | `InViewFeature` mirrors framer's threshold mapping and `onIntersectionUpdate` line for line, and is pinned end to end by four e2e cases |
| **`layout` (all five modes) and `layoutId` within one toplevel** | Pure box math in `createProjectionNode`; the emitted `translate3d`/`scale`/`transform-origin` strings were parsed through a real `CssProvider` on GTK 4.22 |
| **`layoutRoot`** | Already works when paired with `layout`/`layoutId`, and is meaningless without one |
| **Root projection node scroll** | Already at parity with `DocumentProjectionNode` |
| **`AnimatePresence` sync/wait/initial/custom/onExitComplete/propagate** | Pure React context, aliased directly, covered by six e2e cases including 60 rapid toggles |
| **`originZ` truncation** | `stripOriginDepth` is required glue, not a bug: GTK rejects a three-component `transform-origin` |
| **Projection `resetTransform` omission** | Compensated by framer's own `removeTransform` plus the applied-delta strip in `measureInstanceViewportBox` |

| `MotionConfig nonce` | CSP attribute for injected `<style>` tags; gtkx emits through a `Gtk.CssProvider` on the default display | Arrives in props once W6 lands and is harmlessly ignored |
| `LazyMotion` / `m` / `domMin` / `domAnimation` / `domMax` | `loadFeatures` is a global un-scoped merge that would clobber the GTK feature table | Document as intentionally absent, and say why: feature loading is global and would replace `FocusFeature`, `InViewFeature`, and `WidgetProjectionNode`. All nine features are registered eagerly, so every capability the bundles would unlock already works with plain `animated.*` |
